homelab

A language model served from my house that nothing on the internet can reach

No forwarded ports. No reverse proxy, no dynamic DNS, no 0.0.0.0 bind anywhere in the stack. Every service answers from my laptop in another state and from nowhere else — because the network is private rather than firewalled.

The build is the short half. The longer half is six failures and what each one cost.

Proxmox VE 9.1.1 Debian 13 VM llama.cpp 8B Q5_K_M Tailscale WireGuard mesh i5-10500T · 31 GB

The network decision

The usual way to reach a home server from outside is to forward a port on the router. That publishes a service to the entire internet and makes its authentication the only thing standing between strangers and the box.

I used a WireGuard mesh instead. Every device gets a stable private address and can only talk to devices in the same tailnet. The router forwards nothing — from the public internet the house has no open ports at all.

Two consequences worth stating plainly:

  • Addresses stop moving. The mesh address is stable regardless of what the ISP does to the WAN IP or DHCP does to the LAN.
  • Services can be bound narrowly. Because access control is the network's job, a service does not need to listen broadly to be reachable remotely.

The model server is narrower still

It publishes on exactly two sockets — loopback and the mesh address. Not 0.0.0.0. Not the LAN, not the IPv6 interface, not any other tunnel the box happens to have up. Verified rather than assumed: 

$ ss -tlnp | grep 8080
LISTEN 0 4096 127.0.0.1:8080   ...
LISTEN 0 4096 100.x.x.x:8080   ...

$ curl 192.168.1.x:8080   # from another machine on the LAN
curl: (7) Failed to connect — Connection refused

An open model endpoint with no API key is fine when the network is the authentication. It would be reckless on 0.0.0.0.

Six things that broke

The setup is the boring part. This is the part I would want to read.

01

The CPU the VM had was not the CPU the host had

Symptom
llama.cpp refused to run. It needs AVX2.
Cause
Proxmox defaults a VM to a virtual CPU model (x86-64-v2-AES) which does not expose AVX2, even though the physical i5-10500T underneath has it.
Twist
qm set 100 --cpu host still did nothing. A reboot inside the guest never leaves the same qemu process, and the emulated hardware is fixed when that process starts. It needed qm shutdown then qm start.
Lesson
"Restart it" is ambiguous on a VM. Restarting the OS and restarting the machine are different operations, and anything about emulated hardware needs the second one.
02

Proxmox came back from a power cut. The VM did not.

Symptom
Docker unreachable for about two weeks. The hypervisor looked completely healthy.
Cause
The VM's onboot flag was unset, so pve started and left the guest off.
Lesson
Autostart is not a default, and a healthy hypervisor tells you nothing about whether the things on it are running. Every layer reported itself fine, because every layer was fine — nothing owned starting the next layer up. Test recovery by actually cutting power, not by reasoning about it.
03

Locked out, with no console, no key, and no agent

Symptom
Recovering from #2 meant logging into a VM whose password I had forgotten, with no SSH key installed and no guest agent running. Nothing to talk to.
Fix
The hypervisor can edit a guest's disk while the guest is off.
$ qm stop 100
$ LIBGUESTFS_BACKEND=direct virt-customize -a /dev/pve/vm-100-disk-0 \
    --ssh-inject user:file:/path/to/id_ed25519.pub
$ qm start 100
Lesson
On hardware with no BMC or IPMI — which is most consumer hardware — the hypervisor is the out-of-band management path. Worth knowing before you need it, because you cannot look it up from inside the machine you are locked out of.
04

A throwaway container filled the root disk

Symptom
A test container grew to 5.47 GB and took / to 100%. Builds inside it started failing with errors that had nothing to do with disk.
Cause
The VM has 196 GB free on /mnt/data. None of it was in play: Docker's data-root is /var/lib/docker on the 30 GB root disk, which already sits near 85% with the model, a notebook image and Auto-Clipper on it.
Lesson
Know which filesystem your container runtime writes to. Space existing on the machine is not the same as space being available to the thing that needs it.
05

no rules matched

Symptom
Remote SSH stopped working. sshd bound correctly, firewall disabled, iptables on ACCEPT. The box was fine.
$ journalctl -u tailscaled | tail
Drop: TCP{laptop > pve:22} no rules matched
Cause
The tailnet policy was denying it. Tailscale has two policy syntaxes — legacy acls and modern grants — and a file is one or the other, never both. In grants, dst is hosts or identities and ports live in a separate ip field; legacy acls combines them as host:port. Mixing the shapes silently produces a policy that matches nothing.
Lesson
When a connection dies and both endpoints look healthy, something in between is making a policy decision. Find its log before touching either end.
06

The VPN, which took three attempts to diagnose

Symptom
ping to a LAN address succeeded, and every TCP port to every host — 22, 8000, 8006, 9443 — timed out. Both machines, LAN and mesh addresses alike.
Cause
My laptop's VPN kill-switch, defending itself in four layers, each masking the next: "allow local network" silently stopped applying after a relay change; lockdown mode kept blocking after disconnect; split tunnelling had ssh.exe excluded, which blackholes SSH specifically when the tunnel is down while ping keeps working; and residual WFP filters kept blocking even after all three were off. Only fully quitting the client flushed them.
Lesson
"Ping works but nothing connects" is a filter signature, not a routing one. On Windows the filter can outlive the process that installed it. Also: the client was on the far end of every failed connection, and I checked it last. Start with what changed, not with what is complicated.

What I would do differently

  • Move Docker's data-root to the big volume. #4 will happen again otherwise; nothing has actually changed.
  • Fix the model cache mount. The compose file mounts a directory for the model, but -hf downloads to the HuggingFace cache path instead, so the mount is unused and the weights live in the container's writable layer. It survives restarts, but a recreate re-downloads ~5.7 GB.
  • Set BIOS AC recovery to power on. The OptiPlex has no BMC, so this is a physical, at-the-machine change. Until it happens, every power cut needs hands on the box.
